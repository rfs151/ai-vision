1. 加速手段分层

加速手段按位置可以分成五层，越靠上越省事，越靠下改动越大。

① 少推理：降帧检测 + 卡尔曼外推、画面静止跳过、自适应帧率、不同模型不同频率
② 小输入：矩形输入、合适的输入尺寸、YUV 直通、预处理放进模型、只对规则区域切图
③ 小模型：nano 型号、INT8 量化（模型压缩）
④ 跑得巧：线程数调优、关闭绑核、异步推理、多路合批
⑤ 加硬件：核显 / NVIDIA GPU（TensorRT、硬件解码编码）、多主机分布式

3. 可以提升推理性能的方案

# 方案 类别 改动点 预期收益 工作量

实验数据：矩形输入与 INT8 量化

两项都做成了视频实验室的开关（每路单独开关，默认关闭）。对比模式下每 10 次推理用基准（FP32 模型 + 640×640 输入）把同一帧再算一次，对比耗时和检测结果。

测试条件：yolo11n / yolo11n-pose，OpenVINO，每路 2 个推理线程、不绑核。线上 3 路视频同时运行（ped 768×576、still 720×404、fall 姿态模型 640×480），每种设置先等 25 秒稳定，再取 50 秒的中位数。WSL 虚拟机没有开放 AVX-VNNI 指令（CPUID 读出为 0），INT8 走的是 AVX2 整数指令。

线上：单次推理耗时 / Worker CPU

视频 基准（FP32，640×640） 矩形输入 INT8 矩形输入 + INT8
still 720×404 69.7 ms / 68% 48.5 ms（640×384）/ 51% 37.1 ms / 46% 26.5 ms / 35%
ped 768×576 64.0 ms / 66% 51.8 ms（640×480）/ 55% 43.8 ms / 53% 37.5 ms / 45%
fall 640×480（姿态） 65.7 ms / 105% 54.5 ms（640×480）/ 84% 43.0 ms / 77% 36.0 ms / 65%

四种设置下输出帧率都和原视频一致（10 / 15 fps）。

线上：同一帧对比（矩形输入 + INT8 对比基准）

视频 基准 当前设置 检测框一致 置信度变化

离线：纯推理耗时（benchmark_app，2 线程，两轮；后台有 3 路视频在运行，数值有波动）

输入 FP32 INT8
640×640 59–65 ms 31–36 ms
640×384 29–43 ms 20 ms

离线：检测结果一致性（没参与校准的帧，每段视频 30–40 帧）

对比 检测框找回（同类别，IoU ≥ 0.5） 置信度变化
矩形输入 对比 正方形输入（FP32） 100% 交通场景 −0.05，人群场景 −0.01
INT8 对比 FP32（人车检测） 99.1–100% −0.010 ~ +0.039
INT8 对比 FP32（姿态） 100% −0.011；关键点平均偏移约为人身高的 2%

模型大小：yolo11n 10.5 → 2.7 MB，yolo11n-pose 11.5 → 2.9 MB。

结论

  • 两项叠加后，单次推理少 41–62%（still 69.7 → 26.5 ms），Worker CPU 少 32–49%。
  • 矩形输入的收益取决于画面比例：16:9 最多（线上少 30%，离线少 42–44%），4:3 少 17–31%。
  • INT8 在没有 VNNI 指令的情况下，推理仍快 1.5–1.9 倍；在开放了 VNNI 的物理机或服务器上应该更快（待实测）。
  • 精度：没有带人工标注的数据集，只和基准比较了检测框，没有测 mAP。矩形输入在交通场景置信度略降，阈值附近的车会少报一部分；姿态模型叠加两项后置信度降 0.06，摔倒规则是否受影响要再观察。

4. 应用举例：用自然语言查询告警

场景：页面加一个 AI 对话框，输入"最近三天穿黑衣服骑车的人"，系统从告警截图和录像里找出相关记录；选中其中一个人，还能列出他出现过的摄像头，并在三维场景里复现移动轨迹。

4.1 拆开这句话

条件 性质 怎么查
最近三天 时间 SQL 按告警时间筛选
骑车 行为（人 + 自行车/电动车） 检测阶段用规则判定"骑行"，存成类型或标签，SQL 筛选
穿黑衣服 外观 属性字段（上衣颜色 = 黑）走 SQL，或 CLIP 向量检索
出现在哪些摄像头 跨摄像头 ReID 把各路的轨迹合并成同一个全局 ID（见 4.4）
怎么走的、在哪停留 位置和时间 摄像头标定把画面位置换算成平面图坐标，存成轨迹点（见 4.4）

4.2 模块和数据流

4.3 各组件怎么协作

Qwen 怎么知道字段名和取值：不是训练，是后端调用时附上一份"查询工具说明"（JSON Schema），列出参数名、类型、允许取值和中文含义，再给几个示例。Qwen 看不到数据库，工具说明是自己定义的接口层，后端负责把参数转成查询。

{
  "name": "search_alarms",
  "parameters": {
    "since_days": {"type": "integer", "description": "最近几天"},
    "types": {"type": "array", "items": {"enum": ["intrusion", "line_in", "dwell", "fall", "climb", "smoke"]},
              "description": "intrusion=区域入侵，line_in=越线，dwell=逗留，fall=摔倒，climb=翻墙，smoke=抽烟"},
    "tags": {"type": "array", "items": {"enum": ["riding"]}, "description": "riding=骑自行车或电动车"},
    "appearance": {"type": "string", "description": "外观描述原文，如“穿黑色衣服的人”"},
    "device": {"type": "string", "description": "摄像头名称"}
  }
}

不让大模型直接写 SQL：小模型容易写错字段，还可能生成危险语句。由后端检查 JSON（类型必须在允许列表里、天数在合理范围），再用 SQLAlchemy 生成带参数的查询：

q = select(Alarm)
if c.since_days:
    q = q.where(Alarm.created_at >= datetime.now() - timedelta(days=c.since_days))
if c.types:
    q = q.where(Alarm.type.in_([t for t in c.types if t in KNOWN_TYPES]))
rows = session.scalars(q).all()
if c.appearance:
    vec = clip.encode_text(c.appearance)
    rows = sorted(rows, key=lambda a: -cosine(vec, a.embedding))

CLIP 的作用：它有图像编码器和文字编码器，把图片和文字转成同一种向量，内容相符的向量接近。YOLO 只负责框出人（不用训练"黑色衣服"类别），CLIP 判断"长什么样"。截图的向量在入库时算好，查询时只算一次文字，比较几万条向量不到一秒。相似度是相对分数，按分数排序取前 N 条，不设固定阈值。

Qwen（纯文字） CLIP / Chinese-CLIP
输入 整句话 + 工具说明 外观描述；截图
输出 JSON 条件 相似度
要训练吗 不用，靠提示词 不用

属性模型和 CLIP 可以配合：属性模型准、快，但只支持固定几种属性；CLIP 能理解任意描述（"背双肩包戴眼镜"），精度差一些。

不部署本地大模型：用 DeepSeek API 解析查询

查询解析只处理文字（一句话 → JSON 条件），不看图片，所以可以直接调用在线大模型 API（DeepSeek、通义千问等），不用在本地部署 Qwen。做法和本地 Qwen 一样：调用时附上同一份"查询工具说明"，用工具调用（function calling）让模型返回参数，后端照样检查字段、生成 SQL。看图的部分（Chinese-CLIP、ReID、属性模型）在线 API 替代不了，DeepSeek API 只接收文字，这些仍是本地小模型，CPU 就能跑，而且在入库时已经算好。

"最近三天穿黑衣服骑车的人"
   → DeepSeek API（附查询工具说明）← {since_days: 3, tags: ["riding"], appearance: "穿黑色衣服骑车的人"}
   → 后端检查字段 → SQL 筛选
   → 本地 Chinese-CLIP 文字编码器 → 和入库时算好的截图向量比相似度 → 排序
   → 可选：把结果的文字信息（时间、摄像头、数量）发给 DeepSeek 写一句总结
本地 Qwen 3B–4B DeepSeek API
部署 Ollama + 模型文件，内存约 2.5–3 GB 只要 API Key，不占本机资源
一次查询 约 2–5 秒（纯 CPU） 约 1–2 秒（看网络）
解析准确度 简单条件可以，复杂句子偶尔出错 更稳，口语、多条件都能处理
费用 无 按调用量计费，一次查询几百个 token，很便宜
断网 照常使用 不能用，需要备用方案
数据 不出本机 发出的只有问题原文和告警的文字信息；截图、录像、向量都留在本地
  • 断网兜底：后端保留一个规则解析（正则识别"最近 N 天 / N 小时""骑车""黑色"等常用说法），API 调用失败或超时时自动改用，常用查询照样能查。
  • 可切换：DeepSeek、通义千问和 Ollama 都兼容 OpenAI 接口格式，后端只要改 base_url 和模型名，就能在在线 API 和本地 Qwen 之间切换；内网部署、数据不能出网的项目换成本地 Qwen 即可。
  • 和 RAG 的关系：告警记录相当于知识库，SQL 加 CLIP 向量相当于检索。只解析条件时属于工具调用；加上"根据检索结果写总结"这一步，就是完整的 RAG（检索增强生成）。
  • 告警复核不能这样换：5.2 的告警复核要模型看截图，DeepSeek API 不支持图片输入，要用 Qwen-VL 等多模态模型的在线 API 或本地部署。

4.4 跨摄像头关联和轨迹复现

找到"穿黑衣服骑车的人"之后，还可以再往下一步：列出这个人先后出现在哪几个摄像头，并在三维场景里复现他的移动轨迹，停留越久的路段颜色越红。这部分不靠大模型，靠 ReID、摄像头标定和三维可视化三项技术。

ReID 模型（跨摄像头重识别）：ByteTrack 只能在一路画面里跟住同一个人，换了摄像头 ID 就断了。ReID 模型把每条轨迹的截图转成外观特征向量，用法和 CLIP 类似，但它专门训练来区分"是不是同一个人、同一辆车"。不同摄像头的两条轨迹，向量接近且时间、位置说得通，就合并成同一个全局 ID。

  • 行人：OSNet（x0.25 约 20 万参数，x1.0 约 220 万参数）、FastReID 里的模型；车辆：车辆 ReID 模型加车牌识别，有车牌时以车牌为准。
  • 每条轨迹算 1–3 次，CPU 上每次几毫秒到十几毫秒，开销很小。
  • 时空约束：两个摄像头之间正常走路至少要多少秒，比这更快出现在另一边的不合并，可以明显减少误配。
  • 和 CLIP 分工：CLIP 负责从文字描述找到候选，ReID 负责从候选找到同一个人的其他记录。
  • 准确率的风险：视野不重叠、角度和光照差别大、多人穿着相似时容易认错。页面上给出几个候选让值班人员确认，比全自动合并可靠。

摄像头标定（画面坐标 → 地面坐标）：每个摄像头在画面里标 4 个以上地面点（地砖角、车位线角），对应到平面图或地图坐标，用 cv2.findHomography 算出单应矩阵。之后把每个检测框的底边中点（越线规则已经在用的脚底点）乘上这个矩阵，就得到这个人在场地上的位置。所有摄像头换算到同一张平面图上，不同摄像头的轨迹才能接成一条。

  • 每个摄像头标一次，摄像头被挪动后要重标；需要做一个标定页面，在画面和平面图上各点 4 个点。
  • 前提是地面平整；有台阶、坡道时要分区域标定。
  • 视野重叠的区域，同一时刻两路换算出的位置应该接近，可以帮助 ReID 合并。
  • 各路的时间要对齐：摄像头用 NTP 校时，Worker 已经按帧记录时间戳。

轨迹存储：现在只存告警，要复现轨迹就要存每条轨迹的位置序列。按每秒 1 个点抽样，每个点存全局 ID、摄像头、时间、x、y。一个人在画面里待 1 分钟才 60 行，SQLite 足够。

三维展示和停留着色：

  • 场景：先用平面图挤出墙体和道路（2.5D），在地面上画轨迹，演示足够；有 CAD 或 BIM 图纸可以导入，精细建模放到以后。前端用 Three.js（园区、室内）或 Cesium（带经纬度的室外场景）。
  • 停留着色：把轨迹按相邻两点切成小段，每段的停留时间按它覆盖的小块区域里待了多少秒计算，速度越慢停留越久。按停留时间映射颜色，例如 10 秒以内绿色、10–60 秒黄色、60 秒以上红色，效果和地图上的拥堵路段类似。也可以把场地分成网格，统计每格的累计停留时间，画成热力图。
  • 回放：拖动时间轴，人或车的标记沿轨迹移动；点击标记，弹出对应摄像头的截图和录像。

跨摄像头重识别 行人 OSNet / FastReID；车辆 ReID + 车牌识别（导出 ONNX 或 OpenVINO） 几 MB 到几十 MB，CPU 即可
摄像头标定 OpenCV findHomography，新增标定页面 无需额外资源
三维展示 Three.js（园区、室内）或 Cesium（室外、经纬度） 在浏览器里运行
向量存储 SQLite + numpy 逐条比较（几万条以内）；更多时再用 sqlite-vec 或 FAISS 无需额外服务
后端 FastAPI 新增 /api/search 接口 已有
前端 Vue 新增对话框和结果列表 已有

小模型要点：强制 JSON 输出格式（Ollama、llama.cpp 都支持）；关闭 Qwen3 的思考模式；提示词里放几个示例；限制大模型用 4 个线程，避免查询时拖慢视频分析。整套在现有 16 GB 内存的机器上可以和 6 路 Worker 共存（Worker 约 1.6 GB + 模型约 4 GB）。

4.7 可行性

部分 可行性 说明
按时间、类型、摄像头查 高 现有 alarms 表已有 created_at、type、device_id，现在就能做
骑车 中高 COCO 现成类别 + 重叠规则；侧面、遮挡时可能漏判
衣服颜色 中 白天清晰画面效果好；夜间红外画面是黑白的，没有颜色信息；人太小、逆光会出错
跨摄像头关联 中 车辆有车牌时高；行人在角度、光照差别大或穿着相似时容易认错，要人工确认

三维场景 中 平面图挤出（2.5D）工作量小；精细建模要 CAD / BIM 图纸
自然语言解析 高 条件种类有限，DeepSeek API 配工具说明就够，本地 3B–4B 也够用；断网时用规则解析兜底

要提前决定只搜告警，还是搜所有出现过的人。只搜告警最简单，但没触发告警的人搜不到，而"骑车"通常不触发告警；搜所有人要每条轨迹存一张截图和向量，数据量大一些但可控。这个场景建议索引全部轨迹。
