1. 概览

结论

  • 推理加速：运行时调参、多路调度、少推理几帧这几类已经做了，而且都有实测数据。矩形输入和 INT8 量化已经做成视频实验室的开关并实测：两项叠加后单次推理少 41–62%，Worker CPU 少 32–49%，检测框和原来一致（见 3.8）。
  • 多模态：最实用的落地点有两个，一是告警复核（减少误报），二是用自然语言查询告警。两者都不需要大模型看每一帧，YOLO 负责实时初筛，大模型只在少数时刻出场。
  • 动作识别：抽烟、翻墙、投掷最适合的方案是"YOLO 检测物体 + 姿态关键点 + 骨架动作分类"，在 CPU 上能实时运行。不建议用多模态大模型或 SAM 3 做主力。

当前基线（i5-13500H，yolo11n，OpenVINO FP32，640×640 输入）

指标 数值
单路推理（含前后处理） 37 ms/帧
单路 Worker CPU（2 线程，每秒检测 5 次） 约 45%
6 路并发，每路推理 65–90 ms
6 路整机 CPU / 内存 约 44% / 1.6 GB
估算容量 约 10 路

整体分层：加速手段按位置可以分成五层，越靠上越省事，越靠下改动越大。

① 少推理：降帧检测 + 卡尔曼外推、画面静止跳过、自适应帧率、不同模型不同频率
② 小输入：矩形输入、合适的输入尺寸、YUV 直通、预处理放进模型、只对规则区域切图
③ 小模型：nano 型号、INT8 量化（模型压缩）
④ 跑得巧：线程数调优、关闭绑核、异步推理、多路合批
⑤ 加硬件：核显 / NVIDIA GPU（TensorRT、硬件解码编码）、多主机分布式

为什么选 nano（Ultralytics 官方 COCO 数据，以官方文档为准）：

型号 参数量 计算量（GFLOPs） COCO mAP50-95
n（nano，现用） 约 260 万 6.5 39.5
s 约 940 万 21.5 47.0
m 约 2,000 万 68.0 51.5
l 约 2,500 万 86.9 53.4
x 约 5,700 万 194.9 54.7

s 的计算量约是 n 的 3.3 倍，精度高约 7.5 个点。在没有显卡的 CPU 上跑多路，n 是唯一现实的选择；某一路目标都很远很小时，可以单独换成 s。

2.3 检测预算：200 ms 从哪来

默认每秒检测 5 次（--det-fps 5，每个设备可单独设置），两次检测之间 1/5 秒 = 200 ms。一次分析（推理 + 跟踪 + 规则 + 告警截图）要在 200 ms 内做完，才能跟上设定的频率。

位置 内容
worker/worker.py:395 --det-fps，默认 5
api/models.py:21 每个设备保存自己的 det_fps
worker/worker.py:84 self.interval = 1.0 / det_fps
worker/worker.py:168-170 分析完用 200 ms 减去耗时，剩下的休眠

超出 200 ms 时不休眠、紧接着做下一次：视频输出不受影响（画框和编码在另一条线程），但实际检测频率下降，快速移动的目标更容易跟丢或换 ID。

2.4 输入尺寸与 letterbox

YOLO 输入固定为 640×640 正方形。大图按长边等比例缩到 640，短边不足的地方补灰色（114），检测后再把坐标还原到原图。这一步是 detector.py 手写的，因为运行时没有用 Ultralytics 库（它依赖 PyTorch）。补边用 114 是为了和 Ultralytics 训练时一致。

原图 缩放后 灰边占比
1028×480（演示视频） 640×299 约 53%
1920×1080 640×360 约 44%
768×576 640×480 25%

灰边也会被模型算一遍，这是 3.2 节"矩形输入"要省的算力；1920×1080 缩到 1/3 后远处行人只剩十几像素，这是"切图检测"要解决的问题。

3.1 方案总表

9 多主机分布式 扩容 api/manager.py 加节点代理 路数随主机数线性增加 大
10 GPU（TensorRT + 硬件编解码） 加硬件 推理后端、解码编码 单机几十路 大

3.2 模型压缩

INT8 训练后量化（最值得做）

  • 做法（已实现）：scripts/quantize_int8.py 用 OpenVINO 的 NNCF 做训练后量化（PTQ），不用重新训练。校准数据是样例视频每段抽 25 帧（共约 600 帧），按检测器同样的 letterbox 处理，正方形和矩形输入各一半；量化后模型仍是动态尺寸，可以和矩形输入一起用。
  • 检测头里解码框坐标和关键点的运算（加减乘除、DFL）以及 Sigmoid 用 ignored_scope 保留为 FP32，和 Ultralytics 自带的 INT8 导出做法一致。
  • 验证：视频实验室的 INT8 开关 + 对比模式（同一帧和 FP32 基准对比），benchmark_app 测纯推理速度。还没有在带标注的数据集上测 mAP。
  • 硬件：INT8 提速依赖 CPU 指令，AMX > AVX-512 VNNI > AVX-VNNI > 只有 AVX2。本机 WSL 跑在 Hyper-V 虚拟机里，CPUID 读出 AVX-VNNI 为 0，虚拟机没有开放这条指令，INT8 走 AVX2；实测仍快 1.5–1.9 倍（见 3.8）。

其他压缩手段

手段 结论 原因
FP16 CPU 上不做，核显和 GPU 上做 没有 AMX 的 CPU 上基本没收益
结构化剪枝 不建议 要 GPU 重新微调；yolo11n 本身很小，剪完提速有限、精度掉得快
知识蒸馏 不建议单独做 学生模型已经是最小的 n；做新类别训练时可顺带用 s 蒸馏 n
量化感知训练（QAT） 暂不做 PTQ 精度损失超过 3 个点再考虑

3.3 输入与图片处理

矩形输入（已实现）：长边缩到 640，短边只补到 32 的倍数：16:9 → 640×384，4:3 → 640×480（不用补边），1028×480 → 640×320，而不是 640×640。物体缩放比例不变，不用重新训练（Ultralytics 验证时本来就用矩形输入）。固定 640×640 导出的模型把锚点网格写死在图里，改尺寸会报错，所以模型改成 dynamic=True 导出，每种输入尺寸编译一次后缓存。YUV 直通传进来的缩放副本按它自己的尺寸计算，坐标还原不变。实测见 3.8。

预处理放进模型：用 OpenVINO 的 PrePostProcessor 声明输入是 NHWC、uint8、BGR，把 BGR→RGB、转 float、除以 255、NHWC→NCHW 做进模型图里。detect() 只传 letterbox 后的 uint8 图，省掉 numpy 的 transpose 和 astype 拷贝。

关闭不需要的 AI 流编码：项目有两条画框路径。路径 A 由 Worker 把框画进视频再用 x264 编码推回 ai/<name>；路径 B 只把框的坐标发给浏览器，在原始视频上画（见 docs/box-drawing.md）。如果某些路只用路径 B 观看，可以不编码 AI 流，省掉每路的编码开销。告警录像需要的切片要另行处理。

切图检测（借鉴 SAM 3 密集分割 skill 的"多尺度切图"）：

原画面
  ├─ 整图缩到 640 检测一次（找近处的大目标）
  └─ 切成 2×2、相邻重叠 20% 的小图，每块缩到 640 检测（远处小目标变"大"）
        └─ 5 张拼成一批推理 → 各块坐标加偏移换算回原图 → 统一做 NMS 去重
  • 代价：整图切的话推理量约 5 倍。按 37 ms 估算，每次约 150–190 ms，接近 200 ms 预算，要叠加 INT8 才稳。
  • 降低代价：只切画了区域或越线规则的部分，其余用整图；每路单独开关，放进视频实验室做左右对比。
  • 顺带可做"按区域的尺寸 / 宽高比过滤"：框太小、太大或形状不像人就不进规则，压树影、海报误报，改动在 worker/rules.py。

3.4 多个模型：串行还是并行

同一路视频要检测多种事件时，先减少模型数量，再决定怎么调度。以"火焰烟雾、有人摔倒、有人骑车"为例：

事件 需要什么 说明
有人骑车 人 + 自行车/摩托车 COCO 现成类别；"骑车"是规则：人框和车框大面积重叠、人在车上方
有人摔倒 姿态模型 姿态模型也输出人框，可顺带负责检测人
火焰烟雾 自训练模型 COCO 里没有

推荐"姿态模型 + 一个自训练检测模型（自行车、电动车、火焰、烟雾）"，共 2 个模型。

串行还是并行：在 CPU 上，并行不会减少总计算量，6 路已经在分抢核心，并行不能提高总处理能力。

方式 一次分析耗时 总 CPU 复杂度 适合
串行（推荐） 相加，约 40 + 40 = 80 ms 一样 最简单，结果对应同一帧 在 200 ms 预算内
并行（两线程或 OpenVINO 异步） 约等于较慢的一个，约 40 ms 一样，瞬间占用更高 要处理同步 串行超预算且有空闲核心

真正省算力的是不同频率：

时间轴（1 秒）  0     200    400    600    800 ms
姿态模型       ■      ■      ■      ■      ■       每秒 5 次：摔倒是一瞬间，越线要连续跟踪
火焰/骑车模型  ■                                   每秒 1 次：变化慢，骑车的人会停留好几秒
模型 频率 每路约占 CPU
姿态 每秒 5 次 约 20% 单核
火焰烟雾、骑车 每秒 1 次 约 4% 单核

比两个模型都跑 5 次省 40%，再叠加"画面静止跳过推理"还能更省。

进程安排：同一路的多个模型放在同一个 Worker 进程，共用一次解码的帧；不要一个模型一个进程（会重复解码、多占内存）。现在每个 Worker 只加载一个模型（--task detect|pose 二选一，worker/worker.py:389），要支持一路多模型，需要启动参数接受一组模型及各自频率，分析线程按时间表串行调用、合并结果。

3.5 多路合批推理

把几路视频同一时刻的帧叠成一批，让模型一次算完：

现在（每路单独，batch = 1）：
  路1 Worker：帧 → [1, 3, 640, 640] → 模型 → 结果      每路一个进程，各加载一份模型
  ...
  路6 Worker：帧 → [1, 3, 640, 640] → 模型 → 结果

合批（batch = 6）：
  路1 ─┐
  ...  ├─ 各自 letterbox → 叠成 [6, 3, 640, 640] → 推理服务（一份模型）一次推理 → 按路号分回结果
  路6 ─┘

为什么快：小模型单张图填不满硬件，GPU 尤其明显，算 8 张的耗时可能只是 1 张的 1.5–2 倍（示意，需实测）；调度和数据传输等固定开销只付一次；只加载一份模型。

硬件 合批收益 原因
GPU 大，吞吐可能翻几倍 单张图远远填不满 GPU
CPU（本项目） 小 6 进程 × 2 线程已把核心用得差不多，主要省调用开销和内存

代价：各路帧到达时间不同，要设等待窗口（如最多 20 ms），会增加延迟；要新增公共推理进程，各路通过共享内存传帧（每帧约 1.2 MB）；推理服务是单点，需要 api/manager.py 自动重启；一批里尺寸必须相同，和矩形输入冲突，要按尺寸分组。GPU 上现成的方案有 NVIDIA Triton（动态合批）和 DeepStream。

3.6 多主机分布式推理

单机约 10 路是上限，再多就要把 Worker 分到多台主机。现有架构已经具备基础：Worker 只通过网络地址连 ZLM（--src、--dst）和控制服务（--api，拉规则、上报告警和心跳），本身不依赖同一台机器。唯一要改的是 api/manager.py：它现在用 subprocess.Popen 在本机启动 Worker。

控制服务的调度职责：

  • 节点注册：上报核心数、有无 GPU、当前负载。
  • 分配：新流交给负载最低、还有余量的节点。
  • 故障迁移：节点或 Worker 心跳超时，把它的流改派到其他节点。
要点 做法
节点代理 每台主机跑一个小服务，提供"启动 / 停止 Worker、上报负载"的 HTTP 接口；manager.py 从"本机起进程"改成"调用某个节点的接口"
容量 节点按实测容量登记（如 CPU 8 核 ≈ 10 路，GPU 节点更多），调度时不超过上限
网络 每路输入约 1–4 Mbps，加推回的 AI 流，单节点 10 路约几十 Mbps，千兆局域网足够
ZLM 压力 路数很多时可以部署多台 ZLM，或让节点直接从摄像头拉流，只把 AI 流推给 ZLM
规则与告警 已经走 HTTP，无需改动；截图和录像上传到控制服务或共享存储
部署 节点用同一个 Docker 镜像，模型文件打包在镜像里

3.7 按硬件配置的方案

档位 硬件例子 推理方式 解码 / 编码 每台路数（估算） 适合
CPU（现状） i5-13500H、8 vCPU 云主机 OpenVINO FP32 → INT8、矩形输入 CPU（PyAV、x264） 约 10 路（实测估算）；INT8 + 矩形后可能 15–20 路（待实测） 演示、小规模
Intel 核显 / 独显 Iris Xe、Arc A380 OpenVINO device=GPU，FP16 Quick Sync 硬件编解码 待实测；可把推理从 CPU 挪走 本机演示、已有 Intel 平台
入门 NVIDIA RTX 4060 8G、T4 16G TensorRT FP16 / INT8 + 多路合批 NVDEC / NVENC 硬件编解码 几十路，瓶颈通常是解码 中小规模
中端 NVIDIA RTX 4090 24G、L4 24G 同上，另可同机跑本地多模态模型（8B 级）、Qwen、CLIP 同上 几十路 + 本地告警复核和自然语言查询 局域网、要求数据不出内网
服务器 A10、A100、多卡 Triton / DeepStream 整条流水线放 GPU 同上 百路级 大规模平台
边缘设备 Jetson Orin Nano / NX TensorRT INT8 硬件编解码 每台数路 现场就近分析

几点说明：

  • GPU 上推理很快不再是瓶颈：Ultralytics 给出的 yolo11n 在 T4 + TensorRT 上约 1.5 ms/张。每路每秒 5 次时，算力能撑上百路，真正的瓶颈变成视频解码、编码和数据搬运，所以要用 NVDEC / NVENC 硬件编解码，并且尽量让帧一直留在显存里。
  • 消费级显卡有编码路数限制：GeForce 系列驱动限制同时硬件编码的路数（近年约 8 路），数据中心卡（T4、L4、A10）没有这个限制。只用前端画框、不编码 AI 流时不受影响。
  • 换 GPU 后架构要变：从"每路一个进程、各自推理"变成"解码 → 合批推理 → 分发结果"，也就是 3.5 节的方案；NVIDIA DeepStream 就是这种整条流水线的现成实现。
  • NVIDIA GPU 后端：detector.py 已经手写了前后处理，可以加一个 TensorRT 后端，按配置切换 openvino / tensorrt（docs/cv-tech-notes.md 第 6 节）。

3.8 实验数据：矩形输入与 INT8 量化

两项都做成了视频实验室的开关（每路单独开关，默认关闭）。对比模式下每 10 次推理用基准（FP32 模型 + 640×640 输入）把同一帧再算一次，对比耗时和检测结果。

测试条件：yolo11n / yolo11n-pose，OpenVINO，每路 2 个推理线程、不绑核。线上 3 路视频同时运行（ped 768×576、still 720×404、fall 姿态模型 640×480），每种设置先等 25 秒稳定，再取 50 秒的中位数。WSL 虚拟机没有开放 AVX-VNNI 指令（CPUID 读出为 0），INT8 走的是 AVX2 整数指令。

结论

  • 两项叠加后，单次推理少 41–62%（still 69.7 → 26.5 ms），Worker CPU 少 32–49%。
  • 矩形输入的收益取决于画面比例：16:9 最多（线上少 30%，离线少 42–44%），4:3 少 17–31%。
  • INT8 在没有 VNNI 指令的情况下，推理仍快 1.5–1.9 倍；在开放了 VNNI 的物理机或服务器上应该更快（待实测）。
  • 精度：没有带人工标注的数据集，只和基准比较了检测框，没有测 mAP。矩形输入在交通场景置信度略降，阈值附近的车会少报一部分；姿态模型叠加两项后置信度降 0.06，摔倒规则是否受影响要再观察。

4. 动作识别：抽烟、翻墙、投掷

4.1 三个动作的性质不同

动作 特点 单张图能看出来吗 适合的方法
抽烟 关键是香烟这个小物体 + 手靠近嘴 大多能 YOLO 检测香烟 + 姿态规则
翻墙 姿势特别（攀在墙上、腿跨过墙头），也和位置有关 大多能 越线规则 + 姿态判断，或 YOLO 训练"攀爬的人"
投掷 一瞬间的连续动作（举手、甩臂、出手） 很难，单帧和挥手分不清 骨架动作识别

4.2 推荐方案：YOLO + 姿态 + 骨架动作分类

规则合并：

  • 抽烟：骨架判为“手到嘴”，且手附近检测到香烟。
  • 翻墙：骨架判为“攀爬”，且越过围栏线。
  • 投掷：骨架判为“投掷”。
对比 微调多模态大模型（8B） YOLO 单帧检测 骨架动作识别
模型大小 约 5–16 GB 约 5 MB 约 1–5 MB
硬件 24 GB 显卡 CPU CPU
速度 每次 0.5–2 秒 37 ms/帧 1 ms 级（输入只有几十个坐标点）
连续动作 较弱 不能 能
训练数据 图片 + 文字回答 标框的图片 动作视频片段
  • 分类器从简单到复杂：小型 GRU 或 1D-CNN（几十行代码）→ ST-GCN → PoseC3D。
  • 数据：部分公开数据集有类似动作（如 NTU RGB+D 的投掷），抽烟、翻墙可能要用演示视频补充或自己录。
  • 抽烟单靠骨架会和喝水、打电话混淆，必须加香烟检测；香烟很小，建议只裁上半身送检或配合切图。
  • 现在的摔倒检测（worker/fall.py）是手写规则，骨架分类器相当于把它升级成训练出来的模型，摔倒也作为一类。

4.3 为什么不用多模态大模型或 SAM 3 做主力

  • 多模态大模型：微调不会让模型变小（8B 微调完还是 8B），一次推理几百毫秒到几秒，做不到逐帧实时，结果是文字、要解析。适合告警后复核。
  • SAM 3：只会分割，不会判断动作；微调只是让它分割新物体。
  • 局域网环境：主力训练 yolo11n + yolo11n-pose + 骨架分类器；本地 2B 多模态模型作为可选的复核。训练不一定在内网做：数据允许带出去就租云 GPU 训练，再把模型拷进内网。

5. 多模态大模型的应用

5.1 什么是多模态，各模型的分工

"模态"指数据类型（文字、图像、视频、声音、深度、雷达等），多模态就是模型能同时处理两种以上。现在说"多模态大模型"最常指文字 + 图像；声音 + 图像也是多模态。

模型 输入 → 输出 是否多模态 在本项目的位置
yolo11n / pose 图像 → 框、关键点 否 每路实时检测
YOLOE / YOLO-World 图像 + 文字提示 → 框 广义是（视觉-语言） 不训练就能检测新类别
CLIP / Chinese-CLIP 图像、文字 → 向量 是（跨模态检索） 用文字搜截图
SAM 3 图像 + 文字提示 → 轮廓 广义是，但不是大模型 离线自动标注
Qwen（纯文字） 文字 → 文字 / JSON 否 把一句话解析成查询条件
Claude、GPT、Qwen-VL 图像 + 文字 → 文字 是（多模态大模型） 告警复核、描述
YAMNet、PANNs 声音 → 类别 否（和视频配合才是） 声音告警：玻璃破碎、尖叫

总原则：YOLO 等小模型做实时"快筛"，大模型只在少数时刻出场，不看每一帧。

5.2 告警复核

为什么先用 YOLO 初筛：6 路 × 每秒 5 次 = 30 次/秒，每次都调大模型约 259 万次/天，费用和限流都不可行；只在告警时调，每天几十到几百次，约为万分之一。另外 YOLO 一帧 37 ms、大模型一次几秒；断网时本地检测照常工作；只上传少量截图，隐私风险小。有大模型把关后，YOLO 阈值可以放松，漏报和误报都会减少。

方式 例子 优点 缺点

本地部署 Qwen-VL 等开源模型 数据不出内网，不按次收费 要 GPU，效果取决于模型大小

5.3 开放词汇检测（YOLOE / YOLO-World）

输入英文描述（如 "hard hat"）就能检测新类别，不用训练。原理是加了基于 CLIP 的文字编码器，把文字特征和图中区域特征比相似度。

  • 文字在导出时固定：set_classes([...]) 后导出 OpenVINO，推理速度和普通 YOLO 差不多，CPU 可实时；换词要重新导出。
  • 不是什么都能识别：常见物体效果好；安全帽、反光衣能用但误检多；行业专用物体、否定（"没戴安全帽"）、动作和抽象概念效果差。
  • "没戴安全帽"要拆成分别检测 person 和 helmet，再判断头部区域有没有安全帽框。
  • 人、车继续用 yolo11n；需要新类别的那几路单独切到 YOLOE。

6. 应用举例：用自然语言查询告警

场景：页面加一个 AI 对话框，输入"最近三天穿黑衣服骑车的人"，系统从告警截图和录像里找出相关记录；选中其中一个人，还能列出他出现过的摄像头，并在三维场景里复现移动轨迹。

6.1 拆开这句话

条件 性质 怎么查
最近三天 时间 SQL 按告警时间筛选

6.2 模块和数据流

6.3 各组件怎么协作

Qwen 怎么知道字段名和取值：不是训练，是后端调用时附上一份"查询工具说明"（JSON Schema），列出参数名、类型、允许取值和中文含义，再给几个示例。Qwen 看不到数据库，工具说明是自己定义的接口层，后端负责把参数转成查询。

{
  "name": "search_alarms",
  "parameters": {
    "since_days": {"type": "integer", "description": "最近几天"},
    "types": {"type": "array", "items": {"enum": ["intrusion", "line_in", "dwell", "fall", "climb", "smoke"]},
              "description": "intrusion=区域入侵，line_in=越线，dwell=逗留，fall=摔倒，climb=翻墙，smoke=抽烟"},
    "tags": {"type": "array", "items": {"enum": ["riding"]}, "description": "riding=骑自行车或电动车"},
    "appearance": {"type": "string", "description": "外观描述原文，如“穿黑色衣服的人”"},
    "device": {"type": "string", "description": "摄像头名称"}
  }
}

不让大模型直接写 SQL：小模型容易写错字段，还可能生成危险语句。由后端检查 JSON（类型必须在允许列表里、天数在合理范围），再用 SQLAlchemy 生成带参数的查询：

q = select(Alarm)
if c.since_days:
    q = q.where(Alarm.created_at >= datetime.now() - timedelta(days=c.since_days))
if c.types:
    q = q.where(Alarm.type.in_([t for t in c.types if t in KNOWN_TYPES]))
rows = session.scalars(q).all()
if c.appearance:
    vec = clip.encode_text(c.appearance)
    rows = sorted(rows, key=lambda a: -cosine(vec, a.embedding))

CLIP 的作用：它有图像编码器和文字编码器，把图片和文字转成同一种向量，内容相符的向量接近。YOLO 只负责框出人（不用训练"黑色衣服"类别），CLIP 判断"长什么样"。截图的向量在入库时算好，查询时只算一次文字，比较几万条向量不到一秒。相似度是相对分数，按分数排序取前 N 条，不设固定阈值。

Qwen（纯文字） CLIP / Chinese-CLIP
输入 整句话 + 工具说明 外观描述；截图
输出 JSON 条件 相似度
要训练吗 不用，靠提示词 不用

属性模型和 CLIP 可以配合：属性模型准、快，但只支持固定几种属性；CLIP 能理解任意描述（"背双肩包戴眼镜"），精度差一些。

6.4 跨摄像头关联和轨迹复现

找到"穿黑衣服骑车的人"之后，还可以再往下一步：列出这个人先后出现在哪几个摄像头，并在三维场景里复现他的移动轨迹，停留越久的路段颜色越红。这部分不靠大模型，靠 ReID、摄像头标定和三维可视化三项技术。

ReID 模型（跨摄像头重识别）：ByteTrack 只能在一路画面里跟住同一个人，换了摄像头 ID 就断了。ReID 模型把每条轨迹的截图转成外观特征向量，用法和 CLIP 类似，但它专门训练来区分"是不是同一个人、同一辆车"。不同摄像头的两条轨迹，向量接近且时间、位置说得通，就合并成同一个全局 ID。

  • 行人：OSNet（x0.25 约 20 万参数，x1.0 约 220 万参数）、FastReID 里的模型；车辆：车辆 ReID 模型加车牌识别，有车牌时以车牌为准。
  • 每条轨迹算 1–3 次，CPU 上每次几毫秒到十几毫秒，开销很小。
  • 时空约束：两个摄像头之间正常走路至少要多少秒，比这更快出现在另一边的不合并，可以明显减少误配。
  • 和 CLIP 分工：CLIP 负责从文字描述找到候选，ReID 负责从候选找到同一个人的其他记录。
  • 准确率的风险：视野不重叠、角度和光照差别大、多人穿着相似时容易认错。页面上给出几个候选让值班人员确认，比全自动合并可靠。

摄像头标定（画面坐标 → 地面坐标）：每个摄像头在画面里标 4 个以上地面点（地砖角、车位线角），对应到平面图或地图坐标，用 cv2.findHomography 算出单应矩阵。之后把每个检测框的底边中点（越线规则已经在用的脚底点）乘上这个矩阵，就得到这个人在场地上的位置。所有摄像头换算到同一张平面图上，不同摄像头的轨迹才能接成一条。

  • 每个摄像头标一次，摄像头被挪动后要重标；需要做一个标定页面，在画面和平面图上各点 4 个点。
  • 前提是地面平整；有台阶、坡道时要分区域标定。
  • 视野重叠的区域，同一时刻两路换算出的位置应该接近，可以帮助 ReID 合并。
  • 各路的时间要对齐：摄像头用 NTP 校时，Worker 已经按帧记录时间戳。

轨迹存储：现在只存告警，要复现轨迹就要存每条轨迹的位置序列。按每秒 1 个点抽样，每个点存全局 ID、摄像头、时间、x、y。一个人在画面里待 1 分钟才 60 行，SQLite 足够。

三维展示和停留着色：

  • 场景：先用平面图挤出墙体和道路（2.5D），在地面上画轨迹，演示足够；有 CAD 或 BIM 图纸可以导入，精细建模放到以后。前端用 Three.js（园区、室内）或 Cesium（带经纬度的室外场景）。
  • 停留着色：把轨迹按相邻两点切成小段，每段的停留时间按它覆盖的小块区域里待了多少秒计算，速度越慢停留越久。按停留时间映射颜色，例如 10 秒以内绿色、10–60 秒黄色、60 秒以上红色，效果和地图上的拥堵路段类似。也可以把场地分成网格，统计每格的累计停留时间，画成热力图。
  • 回放：拖动时间轴，人或车的标记沿轨迹移动；点击标记，弹出对应摄像头的截图和录像。

部分 可行性 说明

衣服颜色 中 白天清晰画面效果好；夜间红外画面是黑白的，没有颜色信息；人太小、逆光会出错
跨摄像头关联 中 车辆有车牌时高；行人在角度、光照差别大或穿着相似时容易认错，要人工确认

三维场景 中 平面图挤出（2.5D）工作量小；精细建模要 CAD / BIM 图纸
自然语言解析 高 条件种类有限，3B–4B 配工具说明足够；也可以先做下拉框，以后再加大模型

要提前决定只搜告警，还是搜所有出现过的人。只搜告警最简单，但没触发告警的人搜不到，而"骑车"通常不触发告警；搜所有人要每条轨迹存一张截图和向量，数据量大一些但可控。这个场景建议索引全部轨迹。

还缺的：新增标签、属性、向量字段；骑行规则；ReID 模型、全局 ID 和轨迹表；标定页面；三维回放页面；翻墙、抽烟类型要等第 4 节的检测做好后才会出现。

使用方式对比

方式 说明 优点 缺点

应用场景：本项目适合"SAM 3 标注，YOLO-seg 部署"：租云 GPU 用 SAM 3 按文字提示批量生成轮廓，人工修正后训练 yolo11n-seg，导出 OpenVINO 在 CPU 上运行（Ultralytics 的 auto_annotate 就是这种做法）。分割在本项目可用于按人的轮廓做隐私打码，以及用脚下轮廓更准地判断是否进入区域。

SAM 3 密集分割 skill（如"数玉米粒"）是"大模型调度 + SAM 3 + 切图、过滤、精修流程"，只适合离线处理图片；其中的切图思路已借鉴到 3.3 节。
