## 1. 总体思路

**在现有项目里扩展，不新建项目。**

- 项目已经打通“解码 → 推理 → 跟踪 → 规则 → 告警 → 前端”的完整链路，在真实系统里补上训练和加速两段，比孤立的小 demo 更有说服力。
- 架构适合扩展：
  - `worker/detector.py` 自己实现了 letterbox 和 NMS，运行时不依赖 torch，可以再加一个 TensorRT 推理后端，按配置切换 `openvino` / `tensorrt`。
  - 已有 `requirements-export.txt` 和 `scripts/export_model.sh`，模型导出一侧本来就独立。训练代码可以放在新的 `training/` 目录。
- 只有一种情况适合另起项目：要展示和告警平台关系不大的任务，比如分割、OCR、姿态估计。

## 2. 三项技术的定位

“PyTorch 和 TensorRT 是底层框架，所以没法展示”是一个误解。正因为是底层，只调用 `ultralytics` 体现不出能力，要在现成封装**之外**自己动手做事。

| 技术 | 定位 | 展示什么 |
|---|---|---|
| PyTorch | 训练 | 微调新类别；自己写 Dataset、训练循环和 loss，训练 ReID 或属性分类模型并导出 ONNX |
| TensorRT | NVIDIA GPU 推理加速 | 构建 engine、FP16/INT8 量化、动态 batch，以及各推理后端的对比数据 |
| OpenCV | 图像处理 | 视频质量诊断（遮挡、移位、模糊）、运动预筛选、低光照增强、透视变换、隐私打码 |

### 现有模型已经能区分人和车

`yolo11n.pt` 在 COCO 数据集上预训练，能识别 80 个类别，包括 person、car、bus、truck、bicycle、motorcycle 等。项目已经用到了类别：

- 每个检测结果都带类别名（`worker/detector.py`）
- 区域和越线规则都有 `classes` 字段，只有指定类别会触发告警（`worker/rules.py`），例如 `rules/pedestrians.json` 里配置的是 `["person"]`
- 跟踪器只在同类别之间匹配，人和车不会串号

基础模型**做不到**、需要训练的部分：

1. **COCO 里没有的类别**：安全帽、反光衣、烟雾、火焰、电动车（COCO 只有自行车和摩托车）。
2. **细粒度属性**：人的衣服颜色、是否戴帽子、性别和年龄段；车的颜色、车型。常见做法是先用 YOLO 找框，再把框裁出来交给小分类模型。

## 3. 性能影响评估

### 现状（README 7.2、7.3 的实测数据）

- 6 路视频，整机 CPU 约 45%（8 核）。
- 每路 Worker 占 70–85% 的单核，大头是 YOLO 推理：每次 47–63 ms，每秒 5 次。
- 分析的时间预算是每次 200 ms（每秒检测 5 帧），现在只用了 50–60 ms，余量很大。

### 各功能的估算开销（768x432 左右的分辨率）

| 功能 | 做法 | 估算开销 | 影响 |
|---|---|---|---|
| 模糊检测 | 缩小成灰度图，计算拉普拉斯方差，每秒 1 次 | < 1 ms | 可忽略 |
| 遮挡、移位检测 | 亮度、直方图、边缘密度和参考帧对比，每秒 1 次 | 约 1 ms | 可忽略 |
| 运动预筛选（MOG2） | 在缩小的图上做，每秒 5 次 | 1–2 ms | **省 CPU**：画面没动时跳过约 50 ms 的 YOLO |
| 低光照增强（CLAHE） | 只处理送进模型的帧 | 1–3 ms | 很小；只在夜间开启 |
| 透视变换、热力图 | 只变换框的坐标点，累加热力图 | < 1 ms | 可忽略 |
| 隐私打码 | 只处理框内的小区域 | < 1 ms | 可忽略 |
| 微调 YOLO（新类别） | 模型大小不变 | 0 | 无影响；训练在 GPU 机器上做 |
| **ReID / 属性分类** | 对每个框裁剪后再推理 | 每个框 3–5 ms，10 个人时 30–50 ms | **明显**，单路推理耗时可能翻倍 |
| TensorRT | 只在 GPU 机器上做 | 0 | VPS 上不跑 |

### 不拖慢原有 Worker 的原则

- **新功能放在分析线程里，不放进逐帧画框的循环。** 分析线程每次只取最新一帧，偶尔慢一点只是少分析一帧，不会让视频输出卡顿或延迟累积。逐帧路径（解码 → 画框 → 编码）对耗时敏感，不要在那里加处理。
- **降低频率。** 画面质量类检测每秒 1 次就够了。
- OpenCV 的计算会释放 Python 的 GIL，不会和推理线程抢锁。
- **先测再加**：每加一个功能，就在 `stats()` 里加上这个环节的耗时（已有 `infer_ms`），前后各跑一次 `scripts/bench.py` 对比。

### 两个风险点

1. **运动预筛选会影响“逗留”规则。** 人站着不动时，背景建模会判断为“没有运动”，如果因此跳过检测，跟踪会丢失，逗留告警会失效。正确做法：只在“没有运动并且当前没有跟踪目标”时跳过，同时保证至少每 1–2 秒强制检测一次。
2. **ReID 要控制开销。** 只对新出现的目标、匹配有歧义的目标和准备找回的目标提取特征；选小模型（如 osnet_x0_25）并导出为 OpenVINO 格式；多个框合成一批推理。目标是把额外开销压到 10–20%。

## 4. PyTorch：安全帽类别训练

方法是在 `yolo11n.pt` 的基础上继续训练（微调 / 迁移学习），要注意三点。

### 4.1 数据：只有图片不够，必须有标注框

- 每张图都要标出“戴安全帽的头”和“没戴安全帽的头”的位置和类别，通常设两个类别：`helmet`、`head`。
- 要有足够的反例：戴普通帽子的人、光头、背影等，否则模型会把所有帽子都当成安全帽。
- 公开数据集：SHWD（Safety Helmet Wearing Dataset，约 7500 张）、Roboflow 上的 Hard Hat Workers。
- 补充现场图片时用 CVAT 或 LabelImg 标注。

### 4.2 避免“学了新的、忘了旧的”

只用安全帽数据训练，新模型只会输出 helmet/head，原来的人和车就识别不了了。

| 做法 | 推理开销 | 说明 |
|---|---|---|
| 再单独跑一个安全帽模型 | 翻倍 | 最简单，CPU 占用翻倍 |
| **合并数据集一起训练（推荐）** | 不变 | 安全帽数据加上 COCO 里人和车的部分，训练一个同时识别 person/car/helmet/head 的模型，仍然只跑一次推理 |
| 两阶段：先检测人，再裁出头部区域分类 | 每个人加几毫秒 | 分类模型自己用 PyTorch 写，更能体现框架能力 |

### 4.3 训练与部署流程

1. 准备数据集和 `data.yaml`。
2. 在云 GPU 上训练（CPU 训练要几天，GPU 只要几个小时）：
   ```bash
   yolo train model=yolo11n.pt data=helmet.yaml epochs=100 imgsz=640
   ```
3. 评估 mAP，做微调前后的对比。
4. 导出为 OpenVINO 格式，放回 VPS 推理，VPS 不需要 GPU。
5. 代码改动：`worker/detector.py` 里的类别名写死成了 `COCO_NAMES`，要改成从模型文件读取。

## 5. PyTorch：ReID 解决跟踪 ID 跳变

### 5.1 ReID 是什么

ReID（行人重识别）**不是针对某个人训练**，而是训练一个通用的“比较两个人像不像”的模型：

- 用公开数据集（如 Market-1501，包含上千个人在多个摄像头下的图片）训练。模型把每张人像变成一个特征向量（比如 512 维），同一个人的向量靠得近，不同人的向量离得远。
- 训练好以后，新出现的人不需要再训练。给一张某人的截图，算出他的特征，再和所有画面里的人比较，就能找到他。
- 模型一般用 PyTorch 训练。可以用 Market-1501 自己训练，也可以先用现成的预训练模型（如 OSNet），把精力放在接入跟踪器上。

| 用途 | 现在 | 加上 ReID 以后 |
|---|---|---|
| 单路画面内的轨迹 | ByteTrack 能跟踪，靠框的位置和运动预测 | 人被遮挡或交叉走过后，仍保持同一个 ID |
| 跨摄像头、以图搜人 | 做不到，每路的 ID 互相独立 | 在 A 摄像头选中一个人，在 B、C 摄像头里找到他，拼出完整轨迹 |

### 5.2 现在为什么会跳变

`worker/tracker.py` **只靠位置**匹配：用卡尔曼滤波预测框的下一个位置，再和新检测框算重叠度（IoU）。会出问题的三种情况：

1. **遮挡太久**：目标丢失超过 `max_lost_sec=2.0` 秒，旧跟踪会被删除，人再出现时被分配新 ID。
2. **遮挡期间运动改变**：人在遮挡物后停下或转弯，再出现的位置和预测对不上，重叠度太低，变成新 ID。
3. **两人交叉走过**：框重叠时只看位置分不清谁是谁，ID 可能互换。

### 5.3 加入 ReID 后的逻辑

核心思路：匹配时**除了看位置，还要看外观**。这就是 DeepSORT、BoT-SORT 这类跟踪算法的思路。

1. **提取外观特征**：把每个检测框裁出来，送进 ReID 模型，得到特征向量。
2. **每条跟踪记住自己的外观**：用滑动平均更新 `feat = 0.9 * feat + 0.1 * 新特征`。只在框清晰、没有和别人重叠时更新，避免被别人的外观污染。
3. **匹配时综合位置和外观**：
   ```
   代价 = λ × (1 - IoU) + (1 - λ) × 外观距离
   ```
   另加两道门槛：外观差别太大的不允许匹配；位置离得太远、物理上不可能走到的也不允许匹配。交叉时位置分不清，就靠外观区分。
4. **丢失的目标保留更久，按外观找回**：`max_lost_sec` 从 2 秒延长到 10 秒左右，丢失期间保留外观特征。新检测和现有跟踪都匹配不上时，先和丢失的跟踪比外观，相似度够高就沿用原 ID。

```
新检测
  ├─ 和正在跟踪的目标匹配（位置 + 外观）──▶ 成功：沿用 ID
  └─ 没匹配上
       ├─ 和丢失的目标比外观（不要求位置重叠，只要距离合理）──▶ 相似：找回原 ID
       └─ 都不像 ──▶ 分配新 ID
```

现有 ByteTrack 已经有分两轮匹配的结构，把外观距离加进代价矩阵，再加一个“按外观找回”的步骤就行，改动集中在 `tracker.py`。

### 5.4 局限

- ReID 主要靠衣着和体型，**不是人脸识别**。
- 遮挡时间很长、换了衣服、离摄像头太远导致框太小，或者人群中多人穿着相似时，准确率会明显下降。
- ReID 能明显减少跳变，但不能完全消除。

## 6. TensorRT：推理加速

### 6.1 可以展示的内容

- ONNX → TensorRT engine 的构建（`trtexec` 或 Python API）。
- FP16 和 INT8 量化（自己写 INT8 校准器）。
- 动态 batch：把多路视频的帧合成一批推理，贴合“多路摄像头”场景。
- **对比表**：PyTorch / ONNX Runtime / OpenVINO / TRT FP16 / TRT INT8 的延迟、吞吐、显存和 mAP 损失。可以扩展 `scripts/bench.py` 来生成。
- 进阶：预处理（letterbox、归一化）放到 GPU 上做。

### 6.2 硬件限制

TensorRT 只能在 NVIDIA GPU 上运行。本机（i5-13500H）和 VPS 都没有 NVIDIA 显卡，需要租云 GPU（AutoDL 等按小时计费）或使用 Jetson 开发板。代码里做成按配置切换推理后端。

## 7. OpenCV：视频质量诊断与隐私打码

### 7.1 行业叫法：视频质量诊断

安防行业把这类功能统称为**视频质量诊断**，主流安防平台都有这个模块。常见检测项：遮挡、移位、模糊、偏色、亮度异常、雪花噪声、画面冻结、信号丢失。

### 7.2 遮挡检测

**场景**：镜头被挡住了。比如有人故意用布、袋子、喷漆遮住摄像头，或者长期被树叶、蜘蛛网、灰尘挡住。画面还在正常传输，但什么都看不到，没人盯屏幕时可能几天都发现不了。

**判断方法**：

- 大片区域亮度很低或很均匀
- 边缘密度骤降
- 直方图集中在一小段
- 把画面分成网格，可以区分全部遮挡和局部遮挡

### 7.3 移位检测

**场景**：摄像头被人转了方向、被风吹偏，或者维修后没有装回原来的角度。

**和本项目的关系**：告警区域和越线是按画面坐标配置的。摄像头一旦移位，区域就对不上实际位置了，规则会悄悄失效，没有任何报错。

**判断方法**：

- 保存一张参考帧，定期用 ORB 特征点匹配计算偏移，或者用相位相关算平移量。
- 偏移超过阈值时告警“规则可能已失效”。
- 进阶：用算出的单应矩阵**自动校正告警区域坐标**。这是面试亮点，因为它解决的是自己系统里的问题。

### 7.4 模糊检测

**作用**：发现并告警，提醒运维处理，而不是“清晰度不够时做处理”。模糊本身靠软件修复不了，原因多半是物理上的：镜头脏、失焦、起雾、凝水、雨滴挂在镜头上。

**拉普拉斯方差的原理**：拉普拉斯算子提取画面里的边缘和细节（高频成分）。画面清晰时边缘锐利，方差大；画面模糊时边缘被抹平，方差小。

```python
gray = cv2.cvtColor(cv2.resize(frame, (320, 180)), cv2.COLOR_BGR2GRAY)
score = cv2.Laplacian(gray, cv2.CV_64F).var()
```

**常见的坑**：

- 方差和场景内容有关。一面白墙即使很清楚，方差也很低；内容复杂的街景即使有点糊，方差也可能不低。
- 所以不能用固定阈值，要和**这路摄像头自己的基线**比，比如下降到基线的 30% 以下并持续一段时间才判定为模糊。
- 光线暗时噪点会让方差虚高，夜间要单独处理。

### 7.5 工程要点（各检测项通用）

- **自适应基线**：每路场景不同，先学习正常状态，再按相对变化判断。
- **去抖**：异常持续 N 秒才告警，恢复后自动消警。
- **夜间 / 红外切换**：画面变黑白、变暗时要避免误报。
- **拿出数据**：测试视频上的误报率、漏报率，以及每路增加的 CPU 开销。

### 7.6 隐私打码

单独做马赛克很简单，要和检测结合起来才有分量：

- 先用模型找到人脸或车牌，再打码。
- 讲清楚在哪个环节打码：比如实时画面不打码，导出的录像和截图打码，并且打码不可逆。

### 7.7 其他可做的 OpenCV 功能

- **运动预筛选**：背景建模（MOG2），画面没有动静时跳过 YOLO，节省算力（注意第 3 节说的逗留规则风险）。
- **低光照增强**：CLAHE 处理夜间画面，做前后对比图。
- **透视变换**：用单应矩阵把画面转成俯视图，可以估算车速或生成人员轨迹热力图。

### 7.8 项目里已经在用的 OpenCV

- 手写 letterbox 预处理（`worker/detector.py`）
- 用 `cv2.dnn.NMSBoxes` 做按类别的 NMS（`worker/detector.py`）
- 用 `pointPolygonTest` 判断目标是否在区域内（`worker/rules.py`）
- 半透明区域、越线方向箭头、检测框和告警横幅的叠加绘制（`worker/draw.py`）
- 告警截图的 JPEG 编码（`worker/alarm.py`、`worker/apiclient.py`）

## 8. 面试表达建议

- 单说“做过遮挡识别、隐私打码、模糊检测”**分量不够**，每项几行代码就能写出来，一追问细节就露底了。
- 用行业叫法：“做了视频质量诊断模块，覆盖遮挡、移位、模糊等 N 项。”
- 讲难点和处理：自适应基线、去抖、夜间误报、实测数据。
- 讲和系统的结合，最有说服力的一句：
  > 摄像头移位会导致区域规则悄悄失效，所以我用特征点匹配检测移位，并用单应矩阵自动校正区域坐标，在 N 段测试视频上误报率是 X%。
- 先真正做出来、测出数据，再写进简历。

### 可能被追问的问题

| 问题 | 要点 |
|---|---|
| 为什么用拉普拉斯方差判断模糊？ | 模糊会抹掉高频成分，拉普拉斯提取高频，方差反映高频能量 |
| 阈值怎么定？ | 每路自己的基线，按相对下降判断，加持续时间 |
| 夜间怎么处理？ | 亮度过低时暂停模糊判断，或使用单独的夜间基线 |
| 移位怎么检测？ | ORB 特征点 + RANSAC 估计单应矩阵，或相位相关算平移 |
| 运动预筛选会不会漏检？ | 静止目标会被漏掉，所以有跟踪目标时不跳过，并定时强制检测 |
| ReID 怎么减少 ID 跳变？ | 外观特征加入匹配代价，丢失目标按外观找回 |
| 微调后为什么原来的类别没了？ | 灾难性遗忘，需要合并数据集一起训练 |

## 9. 实施顺序

1. **OpenCV**（本机就能做，见效快，风险低）：移位检测与区域自动校正 → 遮挡、模糊 → 运动预筛选。
2. **PyTorch**：微调安全帽类别，或训练 ReID 接进跟踪器（先解决单路遮挡后的 ID 跳变，再做跨摄像头以图搜人）。
3. **TensorRT**：在云 GPU 上做加速，产出各推理后端的对比表。
