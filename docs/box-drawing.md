## 1. 概览

现在有两条画框路径，前面的检测和跟踪是共用的：

- **路径 A：AI 画面**。Worker 用 OpenCV 把框直接画进视频帧，重新编码后推回 ZLM 的 `ai/<name>`。
- **路径 B：原始画面 + 前端画框**。Worker 只把框的坐标发给浏览器，浏览器用 canvas 把框画在原始视频 `live/<name>` 上面。

两条路径都要解决同一个问题：每秒只检测 5 次，但视频每秒有 10–25 帧。解决方法是用卡尔曼滤波估计出的速度，把最近一次的框推算到当前这一帧的位置，这样框能跟着目标平滑移动，不会每 0.2 秒跳一下。

```
PyAV 解码（主线程，每一帧）
  │
  ├─▶ 最新帧槽 ──▶ 分析线程（每秒 5 次，只取最新一帧）
  │                 ① YOLO 检测 → ② ByteTrack 跟踪 → ③ 规则判断
  │                 └─ 生成 track_views（框 + 卡尔曼状态的快照）
  │                      ├─ 路径 B：坐标归一化 → UDP → 控制服务 → WebSocket → 浏览器 canvas
  │                      └─ 有告警：在触发帧上画框 → 告警截图
  │
  └─▶ 路径 A（每一帧）：读取 track_views → 推算到当前帧时间 → OpenCV 画框 → x264 编码 → ai/<name>
```

分析线程每次只处理最新一帧。推理偶尔变慢时，只会少分析几帧，不会让延迟越积越多。

## 2. 检测：得到框的原始坐标

代码：`worker/detector.py` 的 `detect()`

1. **letterbox**：保持宽高比，把画面缩放到 640×640，空白处填灰色（114）。记录缩放比例 `r` 和左、上的填充量 `dx`、`dy`。
2. **推理**：BGR 转成 RGB，HWC 转成 NCHW，归一化到 0–1，交给 OpenVINO 推理。输出格式是 `[4 + 80, N]`，即框的中心 x、中心 y、宽、高，再加 80 个类别分数。
3. **筛选**：每个候选框取分数最高的类别，去掉低于置信度阈值的框，再按配置只保留需要的类别（比如人和车）。
4. **坐标还原**：用 `(坐标 - 填充量) / r` 把 640×640 上的坐标换算回原图坐标。
5. **NMS**：用 `cv2.dnn.NMSBoxes` 去掉重叠的重复框。每个类别的框都加上一个很大的偏移量（类别 id × 10000），保证不同类别的框不会互相抑制，比如人站在车旁边时，人的框不会被车的框去掉。
6. **输出**：`Detection(x1, y1, x2, y2, score, cls, name)`，坐标会裁剪到画面范围内。

## 3. 跟踪：分配 ID 并估计速度

代码：`worker/tracker.py` 的 `ByteTracker.update()`

### 3.1 卡尔曼滤波

- 匀速模型，状态是 `[cx, cy, w, h, vx, vy, vw, vh]`：框的中心、宽高，以及它们的变化速度。
- 时间单位是秒，不是帧数。检测间隔不固定，按实际经过的时间预测才准确。

### 3.2 每次检测后的更新步骤

1. **预测**：每条跟踪按距离上次更新经过的秒数，预测当前位置。
2. **第一轮匹配**：已确认（TRACKED）和已丢失（LOST）的跟踪，与高分检测框按 IoU 匹配（匈牙利算法，只在同类别之间匹配）。
3. **第二轮匹配**：还没匹配上的已确认跟踪，与低分检测框匹配。被遮挡的人分数往往偏低，这一轮能让他们继续保持原来的 ID。仍然没匹配上的跟踪标记为丢失。
4. **第三轮匹配**：试探中（TENTATIVE）的跟踪，与剩下的高分检测框匹配。连续命中 2 次才确认，并分配正式 ID；漏掉一次就丢弃，避免误检产生假目标。
5. **新建跟踪**：剩下的高分检测框创建新的试探跟踪。
6. **清理**：丢失超过 `max_lost_sec`（2 秒）的跟踪被删除。

匹配成功时，用检测框修正卡尔曼状态，同时更新框、分数和锚点（锚点用于越线判断）。

### 3.3 交给画框线程的快照

分析线程调用 `views(tracks)` 生成 **TrackView** 列表。TrackView 是不可修改的快照，包含 id、类别、分数、框、卡尔曼状态和时间。

快照整体替换 `an.track_views`，画框线程直接读取，不需要加锁。跟踪器内部的 Track 对象会继续被修改，但画框线程拿到的快照不会变。

## 4. 路径 A：Worker 把框画进视频

代码：`worker/worker.py` 的 `run_once()` → `render()` → `worker/draw.py`

### 4.1 每一帧的处理

解码出的每一帧都执行一次：

1. `an.submit(img.copy(), t)`：把这一帧的副本放进最新帧槽，供分析线程使用。`t` 是这一帧的时间戳（pts，单位秒）。
2. `render(img, t, ...)`：在这一帧上画出所有内容（见 4.2）。
3. 把画好的原始像素写进 ffmpeg 的标准输入，用 x264（ultrafast、zerolatency）编码，推送到 ZLM `ai/<name>`。同一份编码流还会切成 2 秒的片段，供告警录像使用。

### 4.2 画的内容

| 函数 | 内容 |
|---|---|
| `draw_rules` | 半透明的区域多边形（告警中的区域变成红色）、越线和进入方向箭头、区域人数和越线计数 |
| `draw_tracks` | 每个目标的矩形框和标签 `#id 类别 分数` |
| `draw_status` | 左上角显示输出帧率、推理耗时和目标数 |
| `draw_banner` | 告警后 3 秒内，在底部显示红色横幅 |

### 4.3 框的推算：`TrackView.box_at(t)`

```
dt = clip(t - 最近一次检测的时间, 0, 0.5 秒)
中心 x += vx × dt
中心 y += vy × dt
宽 += vw × dt，高 += vh × dt（最小为 1 像素）
```

- 推算时间上限是 0.5 秒。超过这个时长，推算出的位置更像猜测而不是测量结果。
- 框的颜色按 id 固定生成（`track_color`），同一个目标颜色不变。
- 告警目标改为红色粗框（线宽 3），其他目标线宽 2。

## 5. 路径 B：浏览器在原始视频上画框

### 5.1 Worker 端：发送坐标

代码：`worker/worker.py` 的 `_tracks_payload()` → `worker/apiclient.py` 的 `send_tracks()`

每次分析完成后，把框坐标除以画面宽高，得到 0–1 之间的归一化坐标，连同卡尔曼速度一起打包成 JSON：

```
s:  流名称
a:  这帧到达 Worker 的时间
p:  从这帧到达 Worker 到现在用了多少秒（解码等待 + 推理）
w, h: 画面宽高
tr: [[id, 类别, 分数, x1, y1, x2, y2, vx, vy, 是否告警], ...]
```

- 坐标归一化后，浏览器可以按任意尺寸显示。
- JSON 通过 **UDP** 发给本机的控制服务。丢一包也没关系，下一包 0.2 秒后就到了，而且 UDP 不会因为重传而阻塞分析线程。

### 5.2 控制服务：转发

代码：`api/tracks.py`

收到 UDP 包后，通过 WebSocket 转发给订阅了这一路视频的浏览器。默认只监听本机地址，因为 Worker 和控制服务运行在同一台机器上。

### 5.3 浏览器：对齐时间并画框

代码：`web/src/store.js` → `web/src/components/TrackOverlay.vue`

1. **缓存消息**：收到的每条消息带上接收时间，存进对应流的缓冲区，只保留最近 5 秒。
2. **每次屏幕刷新**（`requestAnimationFrame`，一般每秒 60 次）执行一次：
   1. 用 `contentRect` 计算视频画面在 `<video>` 元素里的实际位置，扣除 `object-fit: contain` 留下的黑边。
   2. 画出区域和越线（来自设备的规则配置，坐标同样是归一化的）。
   3. **对齐时间**：每条消息描述的那一帧，大约在下面这个时刻显示在屏幕上：
      ```
      显示时刻 ≈ 接收时间 − p + 播放器缓冲延迟
      ```
      找到已经显示过的最新一条消息，算出它已经显示了多久（age）。超过 1.5 秒没有新消息，就不画框。
   4. 按 `速度 × min(age, 0.5 秒)` 平移框，换算成像素坐标，用 `strokeRect` 画框，再画标签 `#id 类别 分数`。告警目标显示为红色。

### 5.4 时间对齐的限制

- **WebRTC**：浏览器收到一帧后约 5 ms 就会显示，延迟可以估算，框和人能对齐。
- **HTTP-fMP4**：播放器会缓冲 1–3 秒，延迟没法精确测量，所以监控大屏在这种模式下会关闭前端画框。

## 6. 告警截图里的框

代码：`worker/worker.py` 的 `_process()`

告警截图走的是另一个分支。有告警时，在**触发告警的那一帧**的副本上画区域、框和横幅：

- 用的是这次检测的原始框，不做推算，所以截图里的框和画面完全对齐。
- 触发告警的目标和区域标成红色。
- 同一帧产生的多条告警共用一张截图和一段录像。

## 7. 两条路径对比

| | 路径 A：AI 画面 | 路径 B：前端画框 |
|---|---|---|
| 在哪里画 | Worker，OpenCV | 浏览器，canvas |
| 画框频率 | 视频帧率（10–25fps） | 屏幕刷新率（约 60fps） |
| 视频流 | 重新编码的 `ai/<name>` | 原始的 `live/<name>`，画质无损 |
| 服务器 CPU 开销 | 画框和 x264 编码 | 只发送坐标，几乎没有开销 |
| 时间对齐 | 天然对齐，框直接画在这一帧上 | 依靠 `p` 和播放器延迟估算，只有 WebRTC 准确 |
| 适用场景 | 任何播放方式；录像和截图需要带框 | WebRTC 实时观看，希望画质无损、框移动更平滑 |
