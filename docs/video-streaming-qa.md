## 1. 花屏、跳帧、延迟

### 1.1 花屏

**现象**：画面出现马赛克、绿块、拖影，人走过后留下一串残影，一般要到下一个关键帧（I 帧）才恢复。

**原因**：H.264 的 P 帧只记录和前一帧的差异。只要某个参考帧丢了一部分数据，后面的帧就在错误画面的基础上继续叠加，错误一直扩散到下一个 I 帧。常见的丢数据原因：

| 原因 | 本项目遇到的实例 |
|---|---|
| UDP 丢包 | RTSP 默认走 UDP，网络一抖就丢 |
| 包超过 MTU 被直接丢弃 | 6.4：RTP 包 1472 字节，加上 WebRTC 扩展头和 SRTP 后超过 1500，大包全部丢失 |
| 关键帧太大，一次突发几十上百个包被丢 | 6.5：关键帧 106 KB，WSL 到 Windows 连发 100 个包会丢 15% |
| 解码器中途重启后拿不到 SPS/PPS | 6.5：Windows Chrome 的硬件解码失败，换成软件解码后再也解不出画面 |
| 从非关键帧开始解码 | 新的播放端连进来时恰好在 GOP 中间 |

**解决方案**（括号里是本项目的做法）：

- **传输改用 TCP**：内网推拉流都用 TCP（`rtsp_transport tcp`），丢包重传，不会花屏，代价是网络差时延迟会上升。
- **控制包的大小**：RTP 包控制在 1200 字节（`-pkt_size 1200`），这也是 WebRTC 的常规做法。
- **限制关键帧大小**：用 `-maxrate 1200k -bufsize 300k` 把关键帧从约 135 KB 压到约 30 KB，减小突发流量。
- **每个关键帧前都带 SPS/PPS**：自己编码的流用 `-bsf:v dump_extra=freq=keyframe`；MP4 源直接转推时用 `h264_mp4toannexb`。这样解码器任何时候重启都能恢复。
- **GOP 设成 2 秒**（`-g fps*2`）：即使出错，最多 2 秒就能恢复。
- **WebRTC 自带纠错**：丢包后浏览器自动发 NACK，ZLM 从缓存里重发丢掉的包。实在恢复不了时浏览器会自动发 PLI 请求关键帧，但 ZLM 收到 PLI 不做处理（`webrtc/WebRtcTransport.cpp` 里 PSFB 直接忽略），RTSP 推流端也没有办法响应，所以只能等下一个关键帧。这也是 GOP 要设短、每个关键帧都要带 SPS/PPS 的原因。
- **播放端从关键帧开始**：ZLM 缓存了最近一个 GOP（秒开），新播放端从 I 帧开始拿数据。

编码参数见 `worker/worker.py` 的 `start_encoder`。

### 1.2 跳帧

**现象**：画面一顿一顿，人物瞬移；或者画面突然往前跳几秒。

| 原因 | 解决方案（本项目） |
|---|---|
| 处理速度跟不上，帧在队列里堆积，最后只能整段丢弃 | **只处理最新的一帧**：AI 每秒只检测 5 帧，其余帧靠跟踪器插值画框，输出始终保持原始帧率。处理不过来时直接丢掉旧帧，不排队 |
| B 帧导致解码顺序和显示顺序不一致，WebRTC 播放卡顿 | 编码加 `-bf 0`，不用 B 帧（6.6） |
| 网络抖动，播放端缓冲见底 | WebRTC 由抖动缓冲（jitter buffer）自动调节；fMP4 由浏览器维持约 2.5 秒缓冲 |
| 多路推理抢占同一组 CPU 核 | 关闭 OpenVINO 绑核，推理从 380 ms 降到 62 ms（6.8） |
| 播放器追帧逻辑写错 | fMP4 的追帧逻辑曾把时间戳偏移当成落后，每秒都往前跳（6.7） |

### 1.3 延迟

延迟是整条链路一段一段累加出来的，要逐段测量，逐段处理：

| 环节 | 延迟来源 | 处理方法 |
|---|---|---|
| 编码 | 前向分析（lookahead）、B 帧 | `-preset ultrafast -tune zerolatency -bf 0` |
| 解码 | 帧级多线程会同时解码十几帧，每帧都要等 | **改成片级多线程（SLICE）：1388 ms → 1.5 ms**（6.11，本项目最大的一处延迟） |
| 传输协议 | HLS 6–10 秒，FLV/fMP4 1–3 秒，WebRTC 0.2–0.5 秒 | 实时监控用 WebRTC，兼容性要求高时用 fMP4 |
| 首屏 | 要等到下一个 I 帧才能显示 | ZLM 的 GOP 缓存（秒开）+ 2 秒 GOP |
| 播放端积累 | HTTP 流越播越落后 | 追帧：落后超过 3.5 秒就 1.1 倍速播放，超过 5 秒直接跳到最新（`web/src/components/Player.vue`） |
| 页面切到后台 | Chrome 会暂停后台的视频 | 切回前台时重连，直接跳到最新画面 |

**测量方法**：浏览器端用 `requestVideoFrameCallback` 和 `getStats()`（看 `jitterBufferDelay`）；服务端逐帧记录“收到数据包 → 解码完成 → 推理完成 → 编码完成”的时间戳。本项目就是这样查出 1.4 秒延迟出在解码环节。

## 2. H.264 / H.265 在网页播放

### 2.1 浏览器支持情况

| | H.264 | H.265 |
|---|---|---|
| 原生 `<video>` / MSE | 所有浏览器都支持 | Safari 支持；Chrome、Edge 较新版本只在有硬件解码时支持，没有软件解码兜底；Firefox 支持有限 |
| WebRTC | 所有浏览器都支持 | Safari 支持；Chrome 较新版本才开始支持，同样依赖硬件 |
| HLS | 所有浏览器都能播（hls.js 或原生） | 同上，依赖 MSE 能否解码 H.265 |

**结论**：H.264 可以放心用；H.265 在网页上播放靠不住，同一个页面换一台电脑就可能黑屏。

### 2.2 H.265 的几种方案

1. **服务端转成 H.264（兼容性最好）**：用 ZLM 的 `addFFmpegSource` 或单独的 ffmpeg 进程，把 H.265 拉下来转成 H.264 再推回去。缺点是转码消耗 CPU，路数多时要用 GPU（NVENC 或 QSV）。可以改成**按需转码**：有人看时才启动，没人看就停掉。
2. **用浏览器硬件解码**：MSE 或 WebCodecs（`VideoDecoder`）配合 `hvc1` 编码标识。注意 fMP4 里必须用 `hvc1`，用 `hev1` 时 Safari 不认。
3. **前端软件解码**：把 FFmpeg 编译成 WASM，再用 WebGL 渲染（开源的 Jessibuca 等播放器就是这样做的）。一台普通电脑软解 1080p 大约只能撑 2–4 路，CPU 占用高，只能当兜底方案。
4. **推荐做法：先检测，再选播放方式**：

   ```js
   MediaSource.isTypeSupported('video/mp4; codecs="hvc1.1.6.L120.90"')   // MSE 能否硬解
   await VideoDecoder.isConfigSupported({ codec: 'hvc1.1.6.L120.90' })   // WebCodecs 能否硬解
   ```

   能硬解就直接播放；不能硬解就向服务端请求转好的 H.264 流；服务端也不能转时，最后才用 WASM 软解。

**本项目的情况**：Worker 输出的 AI 画面（`ai/<name>`）一律编码成 H.264，所以带框的画面在任何浏览器都能播放。只有接入的是 H.265 摄像头时，“原始画面”才需要按上面的方案处理。Worker 自己用 PyAV 解码，可以直接解 H.265，不受浏览器限制。

## 3. 视频存储与流式回放

### 3.1 存储

录制格式要和回放方式配套：HLS 点播需要 TS（或 fMP4）切片，ZLM 录出来的普通 MP4 不能直接放进 `.m3u8`。推荐 **TS 大文件 + 字节范围索引**：

- **录制**：每路每小时一个 TS 文件，同目录写一个同名 `.m3u8`，记录文件内部每 10 秒一段的字节范围。用 ffmpeg 的 HLS 输出加 `-hls_flags single_file` 即可，切点自动对齐关键帧（段长要是 GOP 的整数倍，本项目 GOP 2 秒）。录制用 `-c copy`，只写文件不转码，几乎不占 CPU。

  ```
  /record/cam1/2026-10-30/
      1400.ts     ← 14:00–15:00 的录像
      1400.m3u8   ← 1400.ts 的段索引（每段：时长 + 长度@起始字节）
  ```

  ```
  #EXTINF:10.0,
  #EXT-X-BYTERANGE:2480000@2500000
  1400.ts
  ```

- **建索引**：数据库只记文件，例如 `records(stream, start_time, end_time, path, size)`，每路每小时一行。段索引放在 TS 旁边的 `.m3u8` 里，录像和索引一起备份、一起清理；数据库丢了也能扫描磁盘重建。
- **为什么不用 2 秒小切片**：每路每天 43,200 个文件，10 路保存 30 天约 1300 万个文件，目录扫描、清理、备份都很慢。录像只保存几天、路数很少时，也可以简单地用 6–10 秒一个 TS 文件，不用字节范围。
- **估算容量**：2 Mbps 的一路视频，每天约 21.6 GB，保存 30 天约 650 GB。换成 H.265 能省 40%–50%。
- **清理**：按天数或磁盘配额删除最旧的 TS 和对应的 `.m3u8`，同时删掉数据库里的记录。本项目的 `api/retention.py` 清理告警录像时就是这样做的。
- **另一种选择：ZLM 录 MP4**：`enable_mp4=1`、`mp4_max_second=600`（每 10 分钟一个文件），用 `on_record_mp4` 回调把文件信息写进数据库。配置最简单，但回放只能用 3.2 表里的后两种方式（单个 MP4 Range 播放或 ZLM 点播），不能直接做跨文件的 HLS 点播。
- **本项目现状**：常规录像是关闭的（`api/zlm.py` 里 `enable_mp4=0`），只录告警片段。
- **告警录像（`worker/clip.py`）**：编码器多输出一份 2 秒一段的 TS 切片，放在内存目录（`/dev/shm`）里循环覆盖。告警发生后，把"告警前 N 秒 + 告警后 N 秒"对应的切片用 `-c copy` 直接拼成 MP4，不重新编码，只花几毫秒 CPU。这里只保留最近几十秒，切片短反而能截得更准。

### 3.2 流式回放

| 方式 | 做法 | 配套的录制格式 | 适用场景 |
|---|---|---|---|
| **按时间段生成 HLS 点播列表（推荐）** | 查数据库得到时间段覆盖的 TS 文件，读出旁边的 `.m3u8`，截取需要的段拼成一个新的 `.m3u8`（跨文件处加 `#EXT-X-DISCONTINUITY`），hls.js 负责播放和拖动 | TS + 字节范围索引（3.1） | 跨多个文件连续回放，拖到任意时间点 |
| HTTP Range 直接播放 MP4 | `<video src=xxx.mp4>`，浏览器用 Range 请求按需下载；MP4 的 `moov` 必须放在文件开头（faststart） | MP4 | 播放单个片段，例如告警录像 |
| ZLM 点播 | `loadMP4File` 或 ZLM 的 record 点播接口，支持拖动和倍速，也能用 RTSP/WebRTC 回放 | ZLM 录的 MP4 | 需要和直播用同一套播放器 |

**HLS 点播怎么播**：浏览器不会把切片合并成 MP4。hls.js 按每段的字节范围发 Range 请求，只下载要播的那几段，在内存里把 TS 转成 fMP4 交给 MSE 播放，播过的部分随即清理；拖动时直接下载目标所在的段，从段首关键帧解码到目标时间再显示。Safari 原生支持 HLS，不需要 hls.js。需要下载或导出时，再由服务端用 `ffmpeg -i <m3u8> -c copy -movflags +faststart out.mp4` 合并。

**体验细节**：

- **时间轴**：有录像的时段画成色块，断开的时段留空。点击时间轴时，生成从该时刻开始的点播列表，或在已加载的列表里跳到对应时间。
- **倍速**：2 倍速以内直接调 `playbackRate`。4–16 倍速时服务端只发 I 帧（抽帧回放），否则带宽和解码都扛不住。
- **从录像切回直播**：播放器换成直播地址，ZLM 会从 GOP 缓存的 I 帧开始发，切换过程不花屏。

## 4. 4 核 8 GB 能编解码多少路 1080p

### 4.1 实测数据

测试环境：i5-13500H，单线程处理 20 秒的 1080p 25fps 视频（4 Mbps，带噪点，比较接近真实监控画面），用 `ffmpeg -benchmark -threads 1` 统计 CPU 时间。

| 操作 | 占用核数（每路） | 内存（每路） | 4 核理论上限 | 实际可用（留 30% 余量） |
|---|---|---|---|---|
| **只解码** | 0.08 | 64 MB | 约 50 路 | **约 30–35 路** |
| 解码 + 编码（ultrafast） | 0.18 | 100 MB | 约 21 路 | **约 12–15 路** |
| 解码 + 编码（veryfast） | 0.49 | 220 MB | 约 8 路 | **约 5–6 路** |
| 解码 + 编码（medium） | 1.14 | 420 MB | 约 3 路 | **约 2 路** |

复现命令：

```bash
ffmpeg -f lavfi -i "testsrc2=size=1920x1080:rate=25,noise=alls=12:allf=t" -t 20 \
    -c:v libx264 -preset veryfast -b:v 4M -g 50 -bf 0 src1080.mp4
ffmpeg -benchmark -threads 1 -i src1080.mp4 -f null -                                   # 只解码
ffmpeg -benchmark -threads 1 -i src1080.mp4 -c:v libx264 -preset ultrafast -threads 1 -b:v 3M -f null -
```

### 4.2 怎么看这张表

- **内存不是瓶颈**：8 GB 内存足够，瓶颈在 CPU。
- **云服务器要打折扣**：上面是笔记本的高频性能核（4.7 GHz）。云服务器的 vCPU 一般是超线程，频率也低，性能大约是它的 50%–60%，所以 4 核云服务器上：只解码约 15–20 路，ultrafast 转码约 6–8 路，veryfast 转码约 3 路。
- **只转发不转码，CPU 几乎为零**：ZLM 只做转封装（RTSP 转 WebRTC/FLV/HLS），瓶颈变成带宽和网卡，4 核可以转发几百路。所以设计时要**尽量避免转码**。
- **加上 AI 检测会少很多**：本项目每路要“解码 + 每秒 5 次推理 + 画框 + 编码”。实测 6 路 768×432 占整机 45%（8 核），换成 1080p，4 核 8 GB 估计能跑 **4–5 路**。推理分辨率固定是 640，所以推理成本基本不变，增加的主要是解码、画框和编码。
- **想要更多路数就用硬件**：Intel 核显（QSV）或 NVIDIA 显卡（NVDEC/NVENC）可以同时解码几十路 1080p，CPU 只负责调度。

**评估方法**：先用 `ffmpeg -benchmark -threads 1` 测出单路耗时，再按目标路数实际压测。本项目的 `scripts/bench.py` 能看每路的推理耗时和帧率是否跟得上（每秒检测 5 次时，单次推理要小于 200 ms）。

## 5. 根据网络动态调整码率

### 5.1 先确定码率能在哪里调

| 视频来源 | 能怎么调 |
|---|---|
| 浏览器自己推流（WebRTC） | 浏览器内置拥塞控制（GCC，基于 TWCC/REMB 反馈），会自动降码率，不用管 |
| **监控摄像头** | 摄像头的编码参数服务端改不了，只能**在多种码率之间切换** |
| 自己编码的流（例如本项目的 Worker） | 可以直接调编码器的码率 |

### 5.2 方案一：多码率切换（监控行业最常用）

- **准备多种码率**：
  - 摄像头本身有主码流（1080p）和子码流（360p/D1），两路都接入。
  - 没有子码流时，服务端按需转出 1080p、720p、360p 几档。
- **默认规则**：视频墙 9 宫格、16 宫格默认用子码流，单画面放大时切到主码流。这一条最省带宽，效果也最好。
- **HLS/DASH**：主播放列表（master m3u8）里列出多档码率，hls.js 会根据下载速度自动切换。

### 5.3 方案二：自己编码的流，直接调编码器

- **改码率**：ffmpeg 命令行运行中改不了码率。要用 PyAV 或 libx264 的 API（`x264_encoder_reconfig`），或者用 NVENC 的 reconfigure 接口，在运行中调整码率。
- **降帧率**：网络很差时先降帧率，例如 25 fps 降到 10 fps，比降分辨率更不影响看清画面。

### 5.4 判断网络好坏

| 采集位置 | 看哪些指标 |
|---|---|
| WebRTC 播放端 | `getStats()` 里的 `packetsLost`（丢包率）、`jitter`、`jitterBufferDelay`、`framesDropped`、`availableIncomingBitrate` |
| fMP4 / HLS 播放端 | 下载速度（`fetch` 的 reader 统计每秒收到的字节数）、缓冲落后量是否持续变大、`video.getVideoPlaybackQuality()` 的丢帧数 |
| 服务端 | ZLM `getMediaList` 返回的观看人数、每路的发送速率；TCP 发送队列是否堆积 |

### 5.5 切换策略（关键是不要来回抖动）

- **降档要快**：连续 2 次采样（约 4 秒）丢包率超过 5% 或缓冲见底，立即降一档。
- **升档要慢**：连续 15–30 秒都稳定才升一档。升档失败后，等待时间翻倍，避免反复试探。
- **无缝切换**：新码率的流在后台另开一个 `<video>` 拉取。ZLM 会从 I 帧开始发，所以不会花屏。等新画面真正开始播放后再替换旧的，用户只看到清晰度变化，不会黑屏。
- **兜底**：最低档还不行时，降到 1–2 fps 的“快照模式”，或者提示网络较差。

### 5.6 在本项目里怎么落地

现在 Worker 是固定码率（`-crf 23 -maxrate 1200k`）。要支持自适应，最简单的路线是：

1. Worker 多编一路 360p 的子码流（例如 `ai/ped_sub`），两路共用同一次解码和推理，只多一次缩放和编码。
2. 视频墙多宫格时默认用子码流，点开单个画面时用主码流。
3. 播放器按 5.4 的指标采样，按 5.5 的策略自动降档、升档。
